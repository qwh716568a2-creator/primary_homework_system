# 小学课后作业系统数据模型与接口草案

## 1. 说明

本文档用于快速说明 MVP 阶段的核心数据实体、关键关系、状态流转和接口骨架，供研发在详细设计前统一理解。

## 2. 本版账号模型

- 统一账户主表：`user_account`
- 学生资料表：`student_profile`
- 教师资料表：`teacher_profile`
- 家长资料表：`parent_profile`

登录方式：

- 管理员：`user_account.login_name`
- 教师：`teacher_profile.mobile`
- 家长：`parent_profile.mobile`
- 学生：`student_profile.student_no`

## 4. 核心关系

- 一个 `user_account` 只对应一个角色类型
- 一个学生账户对应一条 `student_profile`
- 一个教师账户对应一条 `teacher_profile`
- 一个家长账户对应一条 `parent_profile`
- 一个教师可任教多个班级和学科
- 一个学生可绑定多个家长
- 一条作业可关联多个班级
- 一条作业为每个目标学生生成一条 `student_homework_task`
- 一条任务对应多次提交、多次批改

## 6. 状态流转建议

### 6.1 作业状态

- draft -> published -> closed
- published -> revoked

### 6.2 学生任务状态

- pending -> submitted
- submitted -> completed
- submitted -> revision_required
- revision_required -> submitted
- pending -> overdue
- overdue -> submitted

### 6.3 提交与批改逻辑

- 每次提交写入一条 `homework_submission`
- `student_homework_task` 仅保存最新聚合状态
- 每次批改写入一条 `homework_review`
- 批改为 `revision_required` 时，任务状态更新为 `revision_required`
- 批改为 `completed` 时，任务状态更新为 `completed`

## 8. 开发注意事项

- 登录模块必须按角色分流到对应资料表查询登录标识
- 学生登录建议带 `schoolId`，避免未来多学校学号冲突
- 上传服务建议独立封装，避免主业务接口过重
- 作业任务建议在发布后异步生成
- 所有关键状态变更要保留操作日志
