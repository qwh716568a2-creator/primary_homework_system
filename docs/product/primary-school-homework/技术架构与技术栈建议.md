# 小学课后作业系统技术架构与技术栈建议

## 1. 文档目标

本文档用于明确小学课后作业系统 MVP 阶段的技术架构、终端形态、核心技术栈和非功能性要求，供产品、研发、测试和运维共同决策使用。

## 2. 当前结论

基于小学课后作业系统的业务特点，建议采用“前后端分离 + 单体模块化架构 + 移动端统一跨端方案”的技术路线。

推荐方案如下：

- 教师端：Web
- 管理端：Web
- 学生端：小程序优先，兼容 H5
- 家长端：小程序优先，兼容 H5
- Web 前端：Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus
- 移动端前端：uni-app + Vue 3 + TypeScript
- 后端：Java 17 + Spring Boot 3+maven+Mybatis Plus
- 数据库：MySQL 8
- 缓存：Redis
- 文件存储：阿里云 OSS
- 认证鉴权：JWT + RBAC
- 部署方式：Nginx + Docker

## 3. 技术选型原则

- MVP 优先：优先选择团队容易招聘、容易交付、容易维护的技术。
- 成本可控：尽量复用一套前端技术体系，降低多端开发成本。
- 易扩展：先单体模块化，后续需要时再拆服务。
- 适配场景：满足图片上传、作业批改、消息提醒、统计分析等业务需求。
- 运维简单：适合学校项目、小团队项目或区域试点项目快速落地。

## 4. 整体架构建议

## 4.1 架构形态

MVP 阶段建议采用单体模块化架构，而不是一开始做微服务。

原因：

- 当前核心目标是尽快跑通作业闭环，不是支撑超大规模并发。
- 业务边界虽然清晰，但模块间耦合较高，过早拆服务会增加开发和运维成本。
- 学校项目一般更关注稳定交付和成本控制。

建议模块划分：

- 认证与权限模块
- 组织班级模块
- 作业模块
- 提交模块
- 批改模块
- 通知模块
- 统计模块
- 文件上传模块

## 4.2 架构图说明

- 前端层：教师 Web、管理 Web、学生/家长移动端
- 接入层：Nginx
- 应用层：Spring Boot 单体应用
- 数据层：MySQL、Redis、对象存储
- 外部能力：短信、微信通知、消息推送

## 5. 前端技术栈建议

## 5.1 教师端与管理端

推荐技术栈：

- Vue 3
- TypeScript
- Vite
- Pinia
- Vue Router
- Element Plus
- Axios

选择原因：

- 教师端和管理端页面以表单、表格、筛选、统计页为主，适合 Vue + Element Plus 的后台类开发模式。
- Vue 在国内教育和政企项目中使用广，团队更容易搭建和扩展。
- TypeScript 有利于接口管理、状态管理和长期维护。

适用页面：

- 作业列表
- 发布作业
- 批改页
- 统计页
- 组织与账号管理

## 5.2 学生端与家长端

推荐技术栈：

- uni-app
- Vue 3
- TypeScript

推荐终端策略：

- 首发优先支持微信小程序
- 同时保留 H5 输出能力

选择原因：

- 小学场景下家长高频使用微信，消息触达和打开路径天然更顺。
- 学生和家长端业务以列表、详情、上传、消息为主，uni-app 足够支撑。
- 一套代码兼容小程序和 H5，可降低首期开发成本。

适用页面：

- 我的作业
- 作业详情
- 提交页
- 家长监督页
- 消息页

## 5.3 不建议的前端路线

- 不建议首期分别开发 iOS 和 Android 原生 App
- 不建议首期同时维护 React Web 和小程序原生双体系
- 不建议首期引入过重的低代码平台

## 6. 后端技术栈建议

推荐技术栈：

- Java 17
- Spring Boot 3
- Spring Web
- Spring Validation
- Spring Security 
- MyBatis-Plus
- MapStruct
- Lombok

说明：

- 如果团队更熟悉 Spring Security，可以使用 Spring Security + JWT。
- 如果团队更偏本地化快速交付，也可以使用 Sa-Token 作为会话与权限方案。
- ORM 层推荐 MyBatis-Plus，以提升 CRUD 开发效率，同时保留复杂 SQL 可控性。

选择原因：

- 教育管理类系统对事务一致性、后台管理能力和长期维护性要求较高。
- Java + Spring Boot 在国内交付成熟度高，适合中后台和权限复杂场景。
- 后续如果学校数量、作业量和统计需求增大，也更容易平滑演进。

## 7. 数据与存储建议

## 7.1 关系型数据库

推荐：

- MySQL 8

原因：

- 满足作业、用户、班级、关系绑定、状态统计等结构化数据存储需求。
- 团队使用普遍，维护成本低。

## 7.2 缓存

推荐：

- Redis

使用场景：

- 登录态或 token 黑名单
- 热门班级和作业统计缓存
- 短时消息提醒去重
- 上传临时态或草稿辅助

## 7.3 文件存储

推荐：

- MinIO
- 阿里云 OSS、腾讯云 COS 或同类对象存储

使用场景：

- 学生作业图片
- 作业附件
- 教师批注图片

建议：

- 文件元信息入库，文件实体进对象存储
- 上传前做类型、大小、后缀校验
- 图片支持压缩和缩略图

## 8. 通知与任务调度建议

## 8.1 通知通道

MVP 建议至少支持：

- 站内消息
- 微信消息能力

如学校有要求，可扩展：

- 短信

## 8.2 调度能力

建议用于：

- 截止前提醒
- 逾期催交
- 统计任务

MVP 可选方案：

- Spring 定时任务
- XXL-JOB

建议：

- 单校试点阶段可先用 Spring 定时任务
- 多学校、多策略、多批量任务阶段再接 XXL-JOB

## 9. 接口与鉴权建议

接口风格：

- RESTful API
- JSON 返回

鉴权建议：

- 登录后签发 JWT
- 服务端基于角色与数据范围做 RBAC
- 教师、学生、家长、管理员权限隔离

补充建议：

- 所有关键操作记录审计日志
- 上传、撤回、批改、催交等操作记录操作人和时间

## 10. 部署与运维建议

MVP 推荐：

- Linux 服务器
- Nginx
- Docker
- Docker Compose

环境建议：

- 开发环境
- 测试环境
- 预发布环境
- 生产环境

日志与监控建议：

- 应用日志
- Nginx 访问日志
- 慢 SQL 日志
- 基础告警

如果后期规模扩大，可补充：

- Prometheus
- Grafana
- ELK 或 Loki

## 11. 非功能性要求

## 11.1 性能

- 教师作业列表和学生作业列表首屏响应控制在 2 秒内
- 单次图片上传应有进度反馈
- 发布作业后学生任务生成不应阻塞主请求过久

## 11.2 安全

- 严格控制角色权限和数据隔离
- 文件上传需校验类型和大小
- 关键操作保留审计日志
- 家长仅可访问绑定学生数据

## 11.3 可维护性

- 模块边界清晰
- 统一错误码和接口规范
- 统一日志格式
- 数据库表命名、状态枚举统一管理

## 12. 版本阶段建议

## 12.1 MVP

- 教师端 Web
- 管理端 Web
- 学生/家长 uni-app
- Spring Boot 单体
- MySQL + Redis + 对象存储

## 12.2 V1

- 增强统计能力
- 作业模板
- 批量批改
- 更多通知策略

## 12.3 V2

- 学情分析
- 错题沉淀
- 多学校多租户演进
- 任务中心或独立调度中心

## 13. 最终建议

如果当前没有既定技术约束，建议按以下组合推进：

- Web：Vue 3 + TypeScript + Element Plus+Axios
- 移动端：uni-app + Vue 3 + TypeScript
- 后端：Java 17 + Spring Boot 3 + MyBatis-Plus+Maven
- 基础设施：MySQL 8 + Redis + 阿里云OSS
- 部署：Nginx + Docker

这是一个对小学作业场景来说交付效率、维护成本和后续扩展性比较平衡的方案。
